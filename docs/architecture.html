01

What this is

An internal copilot that helps a Fidelity associate answer a customer's retirement-rollover question in a way that is grounded, compliant, and reviewable — never an autonomous agent talking to the customer.

The associate sends one free-text request. A deterministic router reads it and picks one of two engines; both finish at the same guardrails and the same response shape. The copilot drafts an associate-ready answer — case summary, findings, next steps, required forms, a customer-facing draft, compliance notes, and escalation flags — that the associate reviews before acting. It does not give investment or tax advice, and it never moves money or executes trades.

The one-sentence model One request → router → Path A (live customer data + reasoning) or Path B (standard explanation from approved guidance) → guardrails → associate-ready JSON.

RAG vs MCP — the core distinction

These two sources are deliberately separate, and the difference is the heart of the design. RAG grounds the answer in what Fidelity is allowed to say; MCP grounds it in what is true for this customer.

RAGMCP tools
Answers"What does approved policy say?""What is true about this customer?"

Reached byVector similarity searchExplicit tool call by name

Why it matters for the paths Path A uses both (guidance + live data). Path B uses RAG only and calls no MCP tools — which is exactly why its response shows tools_called: [].
06

MCP tools & data stores

The MCP server (mcp_server/server.py, FastMCP over streamable-HTTP on :8100) exposes seven tools. Six are read-only and are the fixed list Path A calls on every customer-specific request; the seventh is a dry-run write that is exposed but never auto-invoked by the graph. Each takes a single identifier (a CUST-#### id or a full/partial name) and returns a structured record — or { "found": false, … } for an unknown id.

Which database? — none, for the tools The MCP tools do not query Postgres/pgvector. Every tool reads a single flat file, mcp_server/data/mock_customers.json, loaded per call by _data.find_customer() — no SQL, no connection pool. The Postgres + pgvector database is used exclusively by RAG (the rag_chunks table). That separation is the RAG-vs-MCP split: guidance lives in the vector DB, customer facts live behind the tools.

On Path A, call_mcp_tools invokes the six read tools as a fixed batch (that's the 6 tools you see in tools_called). An unknown identifier returns { "found": false, "message": … }, which short-circuits the graph to a clarification rather than guessing.

07

The router

The router is deterministic code (no model call) in classify_request. It looks for rollover intent and whether a specific customer is named, then sets one path.

Request looks like…Path chosenWhy
Rollover question + a specific customer (id or name)A_augmented_llmNeeds live account data → MCP + RAG + reasoning
Rollover question with no specific customerB_prompt_chainA standard explanation → deterministic chain over approved guidance
Not a rollover requestotherFalls into the clarification flow

Because routing is deterministic, the same request always takes the same path — important for an auditable, compliance-sensitive system.

08

The graph

One LangGraph StateGraph holds both paths. They share the front (parse, classify, retrieve) and the tail (guardrails, format), and diverge in the middle.

Shared front
parse_user_request→ classify_request (router)→ retrieve_rag_documents→ route
Path A — Augmented LLM
decide_required_tools→ call_mcp_tools→ synthesize_rollover_plan
Path B — Controlled Prompt Chain
pb_gate (validation)→ pb_explain (step 1)→ pb_build_checklist (step 2)
Shared tail
guardrails_check→ format_final_response→ END

Three places can short-circuit straight to format with a clarification: no customer identifier (decide_required_tools), customer not found (call_mcp_tools), or no grounding available (pb_gate). Every node appends to a trace the UI can show.

General explanation — no specific customer

PATH B · prompt chain

"Explain how a 401(k) to IRA rollover works and what forms are needed."  (no customer_id)

Path taken
parse→ classify → B→ retrieve_rag→ pb_gate · topic=required_forms→ pb_explain→ pb_build_checklist→ guardrails→ format
How the chain works

pb_gate confirms there's grounding (fail-fast if not) and picks a sub-topic. pb_explain drafts a cited plain-language explanation. pb_build_checklist consumes that explanation and produces the standard steps + forms. Each step has a deterministic fallback, so it runs with no API key.

10

Guardrails & escalation

Guardrails are deterministic, code-only checks that run on both paths after synthesis — so the model can't talk its way past them. They are a lightweight stand-in for the future skill-based validation chain.

CheckWhat it does
No investment adviceFlags / neutralizes "you should invest", "allocate X%", "best fund".
No tax/legal adviceFlags tax-outcome claims; defers to a qualified tax professional.
No trade / money movementFlags "execute the trade", "move your funds".
PII redactionRedacts SSN, account numbers, email, phone from the customer draft (associate still sees raw values in findings/trace).
GroundingEnsures rag_sources is populated.

Escalation triggers

Escalation reasons are computed from MCP data. Any one of these escalates; missing application/rollover forms do not (those are normal next steps):

  • Account restriction — fraud hold, KYC gap, beneficiary dispute, address mismatch, blocked account
  • Outstanding loan against the source 401(k) plan
  • Rollover eligibility unknown or not allowed
  • Identity verification missing or incomplete
  • Source-plan details unavailable, or customer record not found

Run it locally

# 1 · database (Postgres + pgvector)
docker compose up -d

# 2 · dependencies
python3 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt -r mcp_server/requirements.txt

# 3 · env + seed + ingest
cp .env.example .env          # optional: set OPENAI_API_KEY for live LLM
python scripts/seed_mock_data.py
python scripts/ingest_docs.py  # 6 docs → 32 chunks

# 4 · MCP tool server (terminal A)
python mcp_server/server.py    # streamable-HTTP on :8100

# 5 · backend (terminal B)
uvicorn app.main:app --app-dir backend --port 8080

# 6 · test — all four flows
bash scripts/smoke_test.sh     # 14 checks
Zero-key by default With no OPENAI_API_KEY, synthesis uses a deterministic offline template; with no sentence-transformers, embeddings use a deterministic hash. pgvector search and MCP calls are real either way — so the demo always runs.
